How AutsPanel works

On this pageOverviewThe website modelJobs and live logsHow a request reaches your siteWhere things are storedSafety rules

AutsPanel is deliberately simple: one Node.js service that drives standard Linux tools. There is no agent network, no proprietary web server and no lock-in — if you uninstall the panel, your nginx sites, apps and databases keep running.

Overview

Browser ──HTTPS──▶ nginx ──▶ AutsPanel (Node.js, port 9090)
                              │
          ┌───────────┬───────┼─────────┬──────────┬─────────┐
          ▼           ▼       ▼         ▼          ▼         ▼
        nginx       PM2    PHP-FPM   MariaDB    certbot    UFW · cron
     (sites)      (apps)  (5.6–8.x)  (databases) (SSL)     rclone (backups)
  • Dashboard: a single-page app in plain JavaScript, served by the panel itself.
  • API: an Express REST API under /api/v1. The dashboard uses exactly the same API you can call from scripts.
  • Tools: AutsPanel calls nginx, pm2, certbot, git, composer, mysql, ufw and rclone. Your input is validated first and passed as separate arguments wherever possible.

The website model

A website record ties together everything that belongs to one site or app:

PartWhat AutsPanel does with it
DomainsAn nginx server block (static, single-page app, PHP, Laravel, WordPress or reverse proxy) and a Let's Encrypt certificate.
CodeA folder, by default /var/www/<name>, optionally a Git repository with a branch.
DeploymentsA deploy script, a history with logs, webhooks and rollback.
RuntimeA PM2 process on its own port (Node.js, Next.js, Python) or a PHP-FPM version.
EnvironmentThe .env file in the site folder.
DatabaseA linked MariaDB/MySQL database and user.
Backups & logsSchedules, backup history, nginx access/error logs and app logs.

When you create a website, AutsPanel looks at the repository (for example package.json, composer.json or requirements.txt) to choose the stack and suggest the build command, start command, web root, a free port and the PHP version.

Jobs and live logs

Anything that takes more than a moment — creating a website, deploying, installing PHP, issuing a certificate, a backup or restore — runs as a job. A job has a list of steps (for example Clone → Install → Build → Start → Health check → nginx → HTTPS), each with its own status, and streams its output to the browser. You can close the page; the job keeps running.

If a setup step fails, fix the cause and click Retry setup: steps that already finished are skipped.

How a request reaches your site

  1. nginx receives the request on port 80/443 and picks the server block by domain.
  2. Static and single-page sites are served from the web root (with an index.html fallback for client-side routes).
  3. PHP, Laravel and WordPress sites are passed to the site's PHP-FPM socket.
  4. Node.js, Next.js and Python apps are proxied to 127.0.0.1:<port>, where PM2 keeps the app running. The app receives its port in the PORT environment variable.

Where things are stored

PathContents
/opt/backup-vpsThe panel's code and .env (admin login).
/opt/backup-vps/server/data/config.json (websites and settings), deployment history and logs, PM2 process files. Credentials files are mode 0600.
/var/www/<name>Website folders (default).
/etc/nginx/sites-available/nginx server blocks, one per website.
/var/log/vps-backup-manager.logJobs, deployments and backups.

Safety rules

  • Every nginx change is checked with nginx -t; if the check fails, the previous configuration is restored.
  • Paths are validated: a website can't be placed in or delete a system folder.
  • The firewall always keeps SSH open, and refuses rules that would block it.
  • Configuration is written atomically, so a crash never leaves a half-written settings file.
  • Panel updates are syntax-checked and rolled back automatically if anything fails.
